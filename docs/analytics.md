# app_events — product analytics

Two instruments, kept on purpose.

| | `src/funnel.js` | `src/analytics.js` |
|---|---|---|
| Goes to | Vercel Analytics | `app_events` in Supabase |
| Holds | counts and short enums | ids: `listing_id`, `partner_id`, `value_pence` |
| Answers | "is the funnel leaking?" | "did the people who saw a locked gem pay?" |

Vercel Analytics is deliberately cookieless and holds nothing to join on, so it
can never answer the second question. That is the whole reason `app_events`
exists rather than being folded into the existing file.

`track()` mirrors the overlapping names (`search`, `gem_view`, `listing_view`,
`submit_spot_done`) into `funnel.js` itself, so a call site wires up one
instrument and gets both. Never call both by hand.

## Adding an event

Two places, and **they must change together**:

1. `KNOWN` in `src/analytics.js`
2. `allowed` in a new migration altering `log_app_event()`

An event in only one of them is dropped on arrival: the call succeeds, the
function returns `false`, nothing is stored, and the dashboard shows a flat
line for a feature that works. `tests/unit/analytics.test.mjs` compares the two
lists and fails if they drift.

## Why an RPC and not an INSERT policy

`app_events` shipped with `"Anyone can log an event"` — an unauthenticated,
unlimited, unvalidated INSERT, the same shape as the `partner_events` hole
flagged in July. `log_app_event()` replaces it and enforces three things a
`WITH CHECK` cannot:

- **Allowlist.** An unknown event name is refused, so the table cannot be
  filled with junk and the dashboard's `GROUP BY` stays meaningful.
- **60 events a minute per session.** A policy has no view of how many the
  session already sent, so the count has to happen somewhere that can read the
  table — which for an anonymous caller means `SECURITY DEFINER`.
- **Shaped `props`.** An object, ≤20 keys, string values truncated to 200
  characters; `path` and `town` capped too.

`user_id` comes from `auth.uid()`, never from a parameter, so a client cannot
attribute its events to somebody else. There is no `user_id` argument to pass.

**Honest limit:** `session_id` is generated by the client, so a determined
caller can rotate it and get another 60. This is a spend and noise control, not
an identity control. The allowlist is what stops the table being *useful* to an
attacker; the rate limit is what stops it being *expensive*.

## What is and isn't recorded

Events carry what the product needs to decide something: which listing was
viewed, which partner was tapped, what a search that found nothing was looking
for. They do **not** carry where a driver's phone is. The coordinates this app
holds are of places people typed, never of the person — the same line
`parking_requests` draws, for the same reason.

## The dashboard

Admin dashboard → **Product metrics** (loads on demand; it is a 30-day
aggregate over every event, and the other panels are what the screen is usually
opened for). It calls `POST /api/admin {action:'metrics'}`, which calls
`app_events_summary()`.

That function is granted to `service_role` only — it reads every user's events,
and the admin endpoint already checks the caller's email against `ADMIN_EMAILS`
before it uses the key.

**Funnel steps count sessions, not taps.** One person opening three locked gems
is one person who wanted them. Counting taps would make the paywall look like
it converts a third as well as it does, which is the kind of error that gets a
working feature deleted.

The **supply list** — `search_no_results` grouped by what was typed, commonest
first — is the one panel meant to be acted on rather than watched. It is the
list of places to go and find a host.
